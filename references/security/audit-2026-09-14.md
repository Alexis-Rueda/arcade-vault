## Hallazgos

### 🔴 Critico

#### 1. `next@16.2.10` — Dependencia con CVEs criticos (RCE, SSRF, middleware bypass)

**Ubicacion:** `node_modules/next` (package.json)
**CWE:** CWE-94 (Remote Code Execution), CWE-918 (SSRF)

El paquete `next` version 16.2.10 contiene 11 CVEs reportados, incluyendo:

- **GHSA-p293-qw3h-jr36** — Unauthenticated Remote Code Execution on windows-hosted servers
- **GHSA-2xp9-vwfh-vxw4** — Unauthenticated RCE in Image Optimization API (AVIF)
- **GHSA-6gpp-xcg3-4w24** — Middleware/Proxy bypass in App Router (Turbopack + single locale)
- **GHSA-89xv-2m56-2m9x** — Server-Side Request Forgery in Server Actions
- **GHSA-m99w-x7hq-7vfj** — Denial of Service in App Router using Server Actions
- **GHSA-p9j2-gv94-2wf4** — SSRF in rewrites via attacker-controlled hostname
- **GHSA-955p-x3mx-jcvp** — Unauthenticated disclosure of internal Server Function endpoints
- Y otros 4 CVEs de DoS y cache confusion.

**Remediacion:** Ejecutar `npm audit fix --force` para actualizar a `next@16.3.5` (fuera del rango declarado, requiere revision de breaking changes). Verificar compatibilidad con las APIs de proxy y App Router antes de actualizar.

### 🟡 Medio

#### 8. `auth_leaked_password_protection` — Leaked Password Protection deshabilitado

**Ubicacion:** Supabase Dashboard > Authentication > Settings
**CWE:** CWE-521 (Weak Password Requirements)

Supabase Auth no verifica contraseñas contra HaveIBeenPwned.org. Usuarios pueden usar contraseñas comprometidas en brechas de datos.

**Remediacion:** En Supabase Dashboard > Authentication > Settings > habilitar "Leaked Password Protection".

#### 9. `auth_rls_initplan` — 3 politicas RLS re-evaluan auth functions por fila

**Ubicacion:** `public.scores` — politicas `scores_insert_auth`, `scores_update_owner`, `scores_delete_owner`
**CWE:** CWE-1188 (Initialization with Hard-Coded Network Resource)

Las politicas usan `auth.uid()` directamente en vez de `(select auth.uid())`. Esto re-evalua la funcion por cada fila escaneada, causando degradacion de performance a escala.

**Remediacion:** Actualizar politicas para usar patron `(select auth.uid())`:
- `scores_insert_auth`: `WITH CHECK ((select auth.uid()) IS NOT NULL)`
- `scores_update_owner`: `USING ((select auth.uid()) = user_id)` + `WITH CHECK ((select auth.uid()) = user_id)`
- `scores_delete_owner`: `USING ((select auth.uid()) = user_id)`

#### 10. `unindexed_foreign_keys` — `scores_user_id_fkey` sin indice coverting

**Ubicacion:** `public.scores` — FK `scores_user_id_fkey`
**CWE:** N/A (Performance)

La foreign key `scores.user_id -> auth.users(id)` no tiene un indice dedicado. Las queries que joined o filtran por `user_id` no pueden usar indices existentes eficientemente.

**Remediacion:** `CREATE INDEX idx_scores_user_id ON public.scores (user_id);`

#### 11. `scores_insert_auth` — INSERT policy solo valida IS NOT NULL

**Ubicacion:** `public.scores` — politica `scores_insert_auth`
**CWE:** CWE-863 (Incorrect Authorization)

La politica de INSERT usa `WITH CHECK (auth.uid() IS NOT NULL)` en lugar de `WITH CHECK (auth.uid() = user_id)`. Cualquier usuario autenticado puede insertar scores con el `user_id` de cualquier otro usuario, permitiendo falsificar puntuaciones en el leaderboard.

Nota: Esto es una decision de diseno intencional documentada en SPEC 14 (seccion Risks), pero desde perspectiva de seguridad es un hallazgo porque un usuario malicioso puede atribuir scores a otros usuarios.

**Remediacion:** Cambiar a `WITH CHECK ((select auth.uid()) = user_id)` para garantizar que cada usuario solo pueda insertar scores propios. Requiere actualizar el `insertScore` function en `lib/supabase/scores.ts` para siempre enviar `user_id` del usuario autenticado.
